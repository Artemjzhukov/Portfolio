# Журнал проекта: микросервис оценки работ (history-rag)

Хронология решений, правок и коммитов. Продукт: FastAPI-сервис, который
принимает работу ученика от n8n, оценивает её (стандартные тесты и ЕГЭ),
делает RAG-анализ пробелов и возвращает структурированный отчёт на русском
для Telegram и Notion.

---

## Фаза 1 — Архитектура и контракты

**Результат:** структура `app/`, Pydantic-схемы, первая рубрика.

- Создан каркас: `app/schemas.py`, `app/config.py`, `app/services/`,
  `data/criteria/history/task_19.json`, `Dockerfile`, `docker-compose.yml`.
- Спроектированы все контракты Pydantic v2: вход `SubmissionInput`
  (file_url XOR file_bytes, валидатор base64), OCR-сегменты, рубрики ЕГЭ
  с **дискретными ступенями баллов** (`deduction_ladder`), оценки LLM,
  выходной `AssessmentResult`.
- Инварианты в схемах: `sum(criteria.max_points) == max_points`, у каждого
  критерия ровно одна ступень `max_points` и одна `points == 0`, уникальные
  `K*`-ID, дубликаты номеров задач в OCR-сегментах запрещены.

**Ключевые решения (по итогам /drill-me стресс-теста архитектуры):**
1. **Парсинг почерка без структуры листа** — двухступенчатый подход:
   Vision-модель только транскрибирует фрагменты в JSON (`task_number: null`
   разрешён, угадывать запрещено), а привязка к номерам задач и merge
   межстраничных фрагментов — детерминированно в коде. Непривязанные
   фрагменты не отбрасываются, а попадают в `unmatched_segments` и предупреждения.
2. **Анти-галлюцинации при снижении баллов ЕГЭ** — strict JSON Schema,
   выбор балла только из ступеней рубрики, обязательная дословная цитата
   ученика для любого снижения, retry при невалидном вердикте,
   `needs_human_review` + RAG-фактчек по хранилищу Qdrant (фактчек только
   добавляет review-флаги, никогда не меняет баллы).
3. **JSON рубрик под валидацию без ошибок** — лестницы вместо свободного
   описания, Pydantic-инварианты, `schema_version`/`year_variant` для версий.

## Фаза 2 — Реализация сервиса

**Результат:** рабочий сквозной пайплайн, 57 тестов, живой смоук-тест.
**Коммит:** `5ffb6fd` (27 файлов).

- `app/services/ocr.py` — определение типа по магическим байтам, pypdf /
  python-docx (включая таблицы бланков), regex-привязка `№N` / «Задание N» /
  «N.», merge сегментов одной задачи с разных страниц, Vision OCR со вторым
  проходом перепроверки неуверенных сегментов.
- `app/services/checker_test.py` — детерминированный движок: нормализация
  (регистр, ё→е, пунктуация), числа («03»=«3»), fuzzy ≥ 0.85 для опечаток,
  множества для мультивыбора, статус `Not Submitted`.
- `app/services/checker_ege.py` — LLM-оценщик по рубрикам + загрузка рубрик
  с проверкой `subject_id`.
- `app/services/llm.py` — единый клиент с retry и JSON-режимом (OpenAI /
  OpenAI-совместимый / Ollama), протокол `LLMClient` для моков в тестах.
- `app/services/rag.py` — `TheoryRetriever` (ленивая инициализация,
  деградация без падения сервиса) + `FactChecker`.
- `app/services/pipeline.py` — оркестрация + русский Markdown-обзор.
- `app/main.py` — `POST /process-submission`, `GET /health`, ошибки
  400/413/422/502, опциональная авторизация `X-API-Key`.
- Тесты (57) по TDD: схемы, движки, оценщик с `FakeLLM`, API с мок-пайплайном.
- Смоук-тест `scripts/smoke_test.py`: реальный запрос → 2/3 (66.7%),
  опечатка «Александр Втрой» зачтена, шапка работы — в предупреждениях.

## Фаза 4 — n8n-готовность: провайдер, асинхронность, Telegram

**Коммиты:** `6c2968a` (OpenRouter), `b3d2c24` (async jobs), текущий (Telegram).

### 4.1 OpenRouter вместо OpenAI
Решение: используем ключи OpenRouter. Реализовано:
- `LLM_BASE_URL=https://openrouter.ai/api/v1` + обычный ключ — весь код
  работает через OpenAI SDK без изменений.
- `LLM_STRICT_JSON=false` — fallback на `json_object` + схема в промпте для
  моделей без Structured Outputs (Pydantic-валидация и retry сохраняются).
- Модели: для оценки ЕГЭ — с поддержкой Structured Outputs; для OCR —
  `openai/gpt-4o` или `google/gemini-2.5-flash`.

### 4.2 Асинхронные джобы + идемпотентность (SQLite только для джоб)
- **Развилка «SQLite vs Qdrant» решена:** Qdrant — семантика (теория,
  фактчек); SQLite — точные ключи (джобы, идемпотентность, аудит).
  Векторная БД для `WHERE job_id = X` — анти-паттерн.
- Порядок «сначала база ответов → потом LLM» подтверждён и уже в ядре:
  `standard_test` не вызывает LLM вообще; в ЕГЭ часть 1 — детерминированно,
  LLM только для части 2. Следующий шаг — хранить эталоны в сервисе,
  чтобы n8n не передавал `answer_key`.
- `POST /process-submission/async` → 202 + `job_id`; `GET /results/{job_id}`
  → статус/результат/ошибка. n8n не держит HTTP-соединение минуты.
- Идемпотентность: `job_id = SHA-256(ученик, предмет, тип, файл, ключи,
  содержимое рубрик)`; повторный POST → мгновенный результат, `reused: true`.
- Джобы >20 мин в queued/running перезапускаются; `error` — при повторном
  POST. SQLite = audit log (кто, когда, какой файл, результат/ошибка).
- Фоновая джоба **всегда** завершается `done` или `error` в сторе — тихих
  пропаж нет.

### 4.3 Telegram-пейлоады из сервиса (n8n остаётся «тупым»)
- `telegram_short` (HTML-режим, ≤3500 знаков): балл + топ-3 проблемных
  задания с усечёнными причинами. Устраняет класс ошибок «сообщение не
  отправилось» (лимит 4096, сломанный MarkdownV2 на произвольном тексте
  ученика).
- Полный отчёт (`summary_feedback`) отправляется **файлом** (send_document).
- `html_escape()` — пользовательский текст безопасен; n8n отправляет одно
  сообщение + один документ, без циклов по заданиям (нет 429).

## Фаза 5 — Операции (в работе)

### 5.1 Структурированное логирование с корреляцией по `job_id`
- `logging.basicConfig` (INFO) в `app/main.py`; модульные логгеры везде.
- Каждый этап логируется с `job=<id>`: приём/повтор/сброс джобы, статистика
  OCR (источник, страницы, сегменты, непривязанные), вердикты ЕГЭ по задачам,
  итоги пайплайна, running/done/error.
- `run()` пайплайна принимает опциональный `job_id` для корреляции; сбои
  внутри джобы логируются с полным traceback (`logger.exception`).
- Тест: `job_id` обязан присутствовать в логах асинхронного потока.

## Бэклог (остаток фазы 5, по приоритету)

1. **n8n-воркфлоу**: webhook → ack в Telegram (из 202) → Wait/poll
   `/results/{job_id}` → Telegram (сообщение + файл) → Notion
   (дедупликация по ключу `student_id + дата + file_hash`, флаг
   `NeedsReview` отдельным checkbox-свойством; имена свойств — английские).
2. **Хранилище эталонов ответов в сервисе** (убрать `answer_key` из payload).
3. Заполнить официальные рубрики ЕГЭ (задания 20–27 и др. предметы).
4. Опционально: `langchain-huggingface` вместо deprecated
   `langchain-community` embeddings.

## Известные ограничения

- Vision OCR рукописей требует модель с Vision (OpenRouter: gpt-4o /
  gemini-flash); чисто текстовые LLM не подходят.
- BackgroundTasks живут в процессе uvicorn: перезапуск контейнера во время
  оценки → джоба останется queued и перезапустится только при повторном
  POST (идемпотентность делает это безопасным).
- Итоговый балл и `percentage` считаются кодом — LLM не влияет на арифметику.
